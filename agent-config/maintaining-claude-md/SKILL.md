# Maintaining CLAUDE.md

`CLAUDE.md` holds what a new joiner needs on day one: conventions, commands, architecture, and the
mistakes the team makes most often. Generated by `/init`, then **cut down**.

> "Keep it under a page, because Claude reads all of it at the start of a session and anything stale
> is taking up context for no benefit."

Every line is paid for in every session, relevant or not. That is the whole economics of this file,
and it is why most of the work here is deletion.

## Where TTMT stands

Measured 2026-08-30 — remeasure (`wc -c CLAUDE.md`) before citing these numbers:

| Repo | `CLAUDE.md` | Loaded every session |
|---|---|---|
| `ttmt-user-service` | 569 lines, **~125 KB** | of which **~100 KB — 80% — is one `## Environment Variables` section** (lines 435–514, some rows over 4,000 characters on a single line) |
| `ttmt-admin` | 382 lines, ~19 KB | proportionate |
| `ttmt-frontend` | 333 lines, ~15 KB | proportionate |
| `ttmt-wiki` | 55 lines | reference material sits in `schema.md` and `AGENTS.md`, read on demand |

user-service is not merely the largest — it is **eight times** its siblings, and the excess is a
single reference table most sessions never consult. Moving it to `docs/` and leaving a pointer is the
largest context saving available anywhere in TTMT, and it costs nothing. The wiki repo shows the
split working.

**There is no second hand-maintained copy any more.** `GEMINI.md` had drifted from `CLAUDE.md` in every
service repo — missing headings, renamed headings, body lines that differed under identical headings —
so on 2026-09-06 the `GEMINI.md` files were deleted and `AGENTS.md` became a symlink to `CLAUDE.md` in
the monorepo root and in each service repo. Every harness now reads one file; never recreate a parallel copy.

The wiki repo shows the split working: `CLAUDE.md` is 55 lines of rules, with the reference material
in `schema.md` and `AGENTS.md`, read only when needed.

## The routing question, answered first

Most requests here are really "where does this rule go?" Four layers, and the wrong one is the common
failure:

| Put it in | When | Nature |
|---|---|---|
| **`CLAUDE.md`** | Needed in *most* sessions in this repo: build and test commands, layout, house conventions, the mistakes made most often | Always loaded |
| **A skill** | Institutional knowledge applied *consistently*, but only on certain tasks | Advisory; loads on trigger |
| **A hook** | The rule must hold without exception | Deterministic: allow, ask, or block |
| **The wiki** | The durable *explanation* — why the rule exists, what broke, what was verified | Queried on demand |

> "Write a skill for institutional knowledge that must be applied consistently; don't write a skill
> for components that belong in CLAUDE.md or a prompt."

And a skill is never the last word on a rule that matters:

> "A skill is a control, though an advisory one… A policy that must always hold needs something
> deterministic behind the skill, such as a hook that blocks the action or a review pass that
> re-checks the policy at the PR."

**Check the hook layer is actually armed before you rely on it.** `ttmt-frontend` has three guard
scripts in `package.json`; `.husky/pre-commit` and `pre-push` run one of them, CI runs two, and
`check:unchecked-supabase-writes` — written after the 2026-08-19 Postgres triage — is invoked by
nothing at all. `ttmt-admin` has no `.github/` directory, so none of its 157 test files run
automatically. A rule you routed to layer 3 is only enforced if something calls it.

## Cutting a large one down

Work by *how often a session needs it*, not by whether it is true:

- **Long reference tables** — environment variables, enum lists, per-service inventories. Needed by a
  minority of sessions, expensive in all of them. Move to `docs/`, leave one line saying where.
- **Per-component deep dives** — one heading per service class. That is what the wiki's `component`
  pages are for; leave the invariant, drop the tour.
- **Anything a linter, a type, or a hook already enforces.** The tool states it at the moment it
  matters; the file does not need to.
- **Rules that apply to one kind of task.** That is a skill, and it is currently taxing every session.
- **Anything a reader would have to verify before trusting.** Stale beats absent only in this file's
  own opinion of itself.

What stays: the commands (`npm run test`, `npm run test:gate`, `npm run check`), the boundaries of the
service, the strict rules, and `## Things Claude gets wrong`.

## When to write

> "When Claude makes a mistake twice, the correction goes into CLAUDE.md."

Twice, not once. One mistake is noise; the second is a pattern with evidence. Corrections land in
`## Things Claude gets wrong`, phrased as the correction rather than the story. `running-review-passes`
feeds this: a mistake flagged for the second time is corrected **in that review**, not filed for later.

**Every rule you add names its wiki page.** The correction is the line in `CLAUDE.md`; the evidence —
what broke, when, what was verified — belongs on a wiki page, and the line carries the pointer. One
trailing `— see ttmt-wiki/wiki/<page>.md` is the whole cost.

Without it a rule cannot be audited. Nobody can tell whether it is still true, which is how this
repo's root `CLAUDE.md` came to assert a wiki size that was out by a factor of three: a claim with no
route back to its source is never re-checked, only re-read. If the rule has no page yet, that is the
signal to write the source and `/wiki-ingest` it — not to skip the pointer.

> **Do not state a rule here without a route back to its evidence.** Reason: an unsourced rule in an
> always-loaded file is indistinguishable from a stale one, so it survives long after the behaviour it
> described changed — and every session pays for it. Instead: link the wiki page, or write it.

## Boundaries

> **Do not put policy in `CLAUDE.md`.** Reason: policy is long, changes on its own schedule, and
> applies to a minority of sessions, so it displaces context in every session that does not need it.
> Instead: a skill carries the policy and loads when it applies; `CLAUDE.md` keeps at most a pointer.

> **Do not leave a must-always-hold rule as prose.** Reason: `CLAUDE.md` is advisory in exactly the way
> a skill is, so a rule stated there is one distracted session away from being violated. Instead: back
> it with a hook, and let the block explain itself.

> **Do not maintain a second always-loaded file by hand.** Reason: two hand-maintained copies drift —
> this repo's `GEMINI.md` files did, until they were replaced by `AGENTS.md` symlinks to `CLAUDE.md`.
> Instead: keep one file; any other harness's entry file is a symlink to it.

> **Do not grow this file to be thorough.** Reason: thoroughness is measured against a fixed budget —
> the context every session spends before reading any code. Instead: when it passes a page, move the
> least-often-needed section out and leave a pointer.

## Verification block

The playbook's example ends its verification instructions with the line worth carrying in every repo:

> "If a test fails, fix the code, not the test."

`writing-the-failing-test-first` is the discipline behind that sentence — including the four ways a
TTMT suite passes without proving anything.
